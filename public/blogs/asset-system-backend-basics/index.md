实习的前两周，我接手了一个设备资产管理系统。它负责管理每台设备从入库、发货、部署、使用到维修、报废的整个过程。这篇文章按知识点，整理我在这个项目里碰到的后端基础问题，包括表设计、唯一标识、跨系统数据同步、SQL 查询、会话认证和并发控制。

文中的表名和代码都简化过，只保留和概念相关的部分。

---

## 一、表设计：一对多与外键

系统里有三个核心概念：

- **租户**：使用设备的客户单位
- **站点**：客户名下设备实际摆放的地点
- **部署**：一条记录，表示“某台设备在某段时间部署在某个站点”

它们之间是两层一对多关系：一个租户有多个站点，一个站点有多条部署记录。

```txt
tenants (id, name)
   ▲ 1
   │
   │ N
sites (id, tenant_id → tenants.id, name)
   ▲ 1
   │
   │ N
deployments (id, site_id → sites.id, asset_id, status, ...)
```

**规则：外键放在“多”的那一方。** 站点表存 `tenant_id`，部署表存 `site_id`。

为什么不在租户表里存一个站点 id 列表，比如 `"S1,S2"`？

1. 数据库没法给一个字符串里的多个 id 建外键，也就没法检查这些 id 是否真实存在。
2. 每新增一个站点，都要回头修改租户那一行。并发写入时，容易覆盖别人刚做的修改。
3. 查“某个站点属于哪个租户”，只能在每个租户的字符串里逐个搜索。

外键还带来一个设计约束：**被引用的数据只能停用，不能删除。** 部署记录引用了站点，站点一删，历史部署就失去了指向，数据库的外键约束也不会允许这样删。所以基础资料一律用 `status` 字段做启用和停用的软状态。

## 二、唯一标识：设备序列号（SN）

资产系统和另一个设备平台各自给设备生成主键，两边的 id 没有任何关系。两个系统之间唯一共同的字段，是设备出厂时厂家编的序列号（SN）。所以 SN 承担了**跨系统识别同一台设备**的作用。

既然是唯一的识别依据，SN 就必须唯一，而且写入前要先标准化：

```python
def normalize_sn(raw: str) -> str:
    value = raw.strip().upper()          # 去首尾空白，统一大写
    if not value or value in {"-", "未知"}:
        raise ValueError("无效的 SN")
    return value                         # 中间的 - 和 _ 保留
```

| 规则 | 原因 |
|---|---|
| 去首尾空白、转大写 | `" ab-12 "` 和 `"AB-12"` 是同一台设备，不处理就会建出两份档案 |
| 保留中间的 `-`、`_` | `AB-12` 和 `AB12` 可能是两台不同的设备，不能误合并 |
| 拒绝空值、`-`、“未知” | 否则所有 SN 未知的设备都会撞在同一个值上 |
| 保留原始值 | 用于审计，能追溯当初录入的是什么 |
| 数据库唯一约束（只在未作废的资产中生效） | 新增、换机、更正时都由数据库兜底拦截重复 |

另外，SN 不能通过普通编辑修改，只能走专门的“更正 SN”操作，旧值存进 `previous_sns`。原因是 SN 一旦被悄悄改掉，另一个平台就再也对不上这台设备了。

## 三、跨系统数据：只读副本与定时同步

租户和站点由另一个平台维护，资产系统不是这份数据的主人。但资产系统仍然在本地存了一份，放在 `scenarios` 表里。

### 为什么要存本地

- **外键需要本地表。** `deployments.site_id` 是外键，外键只能指向同一个数据库里的表。
- **查询需要关联。** 统计“每个站点有几台设备在用”，要把部署表和站点表放在一起查，跨系统做不了。
- **降低对外部系统的依赖。** 对方接口短暂不可用时，本系统的发货、查询功能不受影响。

### 为什么只读

本地这份只是副本。如果在本地修改，下次同步会把改动覆盖掉，覆盖之前两边的数据也对不上。所以要修改，只能去数据的主人那边改。

### 同步怎么做

一个定时任务（worker）每隔一段时间拉取对方的全部站点，按对方的站点 id（`source_id`）和本地数据逐条对照：

```python
async def sync_sites(db, items: list[dict]):
    existing = {row.source_id: row for row in await load_all_sites(db)}
    seen = set()

    for item in items:
        seen.add(item["id"])
        row = existing.get(item["id"])
        if row is None:
            db.add(Site(source_id=item["id"], **to_fields(item)))   # 新增
        else:
            update_if_changed(row, item)                            # 更新

    if not items:
        return    # 返回 0 条通常是对方异常，不能据此停用全部站点

    for source_id, row in existing.items():
        if source_id not in seen:
            row.status = "disabled"    # 对方不再返回的：只停用，不删除
```

这里有三个设计点：

1. **按 `source_id` 对应，不按名称。** 名称会改，也可能重名，只有 id 是稳定的。
2. **消失的站点只停用、不删除。** 部署记录还引用着它们，删除会破坏历史数据。
3. **空结果不做停用。** 对方接口出问题时返回 0 条，如果照常处理，会把所有站点一次性停用。

## 四、快照与引用

部署表里同时存了 `site_id` 和 `site_name` 两列：

| 列 | 类型 | 内容 |
|---|---|---|
| `site_id` | 引用（外键） | 指向站点本身，查到的是站点**现在**的信息 |
| `site_name` | 快照 | 发货那一刻复制下来的名称，之后不会再变 |

例子：3 月，一台设备发往“阳光小区”；5 月，站点改名为“阳光花园”。

- 3 月那条部署记录的快照，仍然是“阳光小区”，和当时的出库单、签收单一致。
- 通过 `site_id` 查站点表，得到的是现在的名字“阳光花园”。

需求的规则是：**当前部署显示最新值（读引用），历史部署保留快照。** 如果只存 `site_id`，每次都现查站点表，那么站点一改名，所有历史单据上的名字都会跟着变，记录的就不再是当时的事实。

## 五、SQL：聚合查询与 N+1

站点列表每页 20 个站点，每个站点要显示“在用几台、部署中几台”：

```sql
SELECT site_id, status, COUNT(*)
FROM deployments
WHERE site_id IN (:site_ids)        -- 本页 20 个站点
  AND status IN ('active', 'planned')
GROUP BY site_id, status;
```

按执行顺序来理解：

1. `FROM`：从部署表取数据
2. `WHERE`：只保留本页站点的、状态为在用或部署中的行
3. `GROUP BY site_id, status`：站点和状态都相同的行归为一组
4. `SELECT ... COUNT(*)`：每组输出一行，`COUNT(*)` 统计的是**这一组**的行数

比如站点 A 有 2 台在用、1 台部署中，站点 B 有 1 台在用，结果就是：

| site_id | status | count |
|---|---|---|
| A | active | 2 |
| A | planned | 1 |
| B | active | 1 |

没有出现在结果里的组合，比如 B 的 planned，在代码里按 0 处理。

**为什么不循环查询？** 如果对每个站点单独执行一次 `COUNT`，查 1 次列表之后还要再查 N 次，这就是 **N+1 问题**。每次查询都有一次和数据库之间的网络往返，20 个站点就是 20 次往返。用 `IN` 加 `GROUP BY`，一次查询就能拿到全部结果。

## 六、SQL：JOIN 与 LEFT JOIN

需求：列出所有站点和站点上正在使用的设备 SN，**没有设备的站点也要显示**。SN 存在资产表里，所以要经过部署表再连到资产表：

```sql
SELECT s.name, a.sn
FROM sites s
LEFT JOIN deployments d ON d.site_id = s.id AND d.status = 'active'
LEFT JOIN assets a      ON a.id = d.asset_id;
```

注意 `d.status = 'active'` 写在 `ON` 里，而不是 `WHERE` 里。如果写成 `WHERE d.status = 'active'`，没有设备的站点那一行 `d.status` 是 `NULL`，会被 `WHERE` 过滤掉，`LEFT JOIN` 就退化成了 `JOIN`。

| 写法 | 保留哪些行 | 没有设备的站点 |
|---|---|---|
| `JOIN` | 只保留两边都能匹配上的行 | 整行消失 |
| `LEFT JOIN` | 左表的行全部保留，右表匹配不上就填 `NULL` | 保留，`sn` 为 `NULL` |

两个容易混淆的点：

- **哪张表放左边，看的不是哪张表行数多**，而是哪张表的数据一行都不能少。这里要求“所有站点”，所以站点表放左边。
- **`JOIN` 不分左右**，`A JOIN B` 和 `B JOIN A` 的结果行是一样的；只有 `LEFT JOIN` 的左右顺序会影响结果。

## 七、会话认证：为什么用 Redis

HTTP 是无状态协议，服务端不会记得上一个请求是谁发的。所以登录之后，客户端要在每个请求里带上凭证：

```http
Authorization: Bearer <token>
```

登录成功时，服务端生成一个随机 token，把 `token → 用户 ID` 存进 Redis，并设置过期时间：

```txt
SET session:token:<token> <user_id> EX 1800
```

**为什么不存在后端进程的内存里？**

1. **进程重启会丢。** 内存属于进程，进程一退出，所有会话都会失效。
2. **多实例之间不共享。** 生产环境通常同时运行多个后端实例，前面用负载均衡分发请求。在实例 1 登录后，下一个请求可能被分到实例 2，而实例 2 读不到实例 1 的内存。

Redis 是一个独立的进程，所有后端实例都连接同一个 Redis，后端重启也不影响它。和存在 PostgreSQL 相比，Redis 读写更快，而且原生支持 TTL 过期，不需要自己写定时任务去清理过期会话。

**程序之间的调用用 API Key。** 同步站点的定时任务没有浏览器，也不会走登录流程，所以给它分配一个长期有效的 API Key。

**401 和 403 的区别：**

- `401 Unauthorized`：服务端不知道你是谁，比如没带凭证，或凭证无效、已过期。
- `403 Forbidden`：服务端知道你是谁，但你没有这个操作的权限。

## 八、并发：先查后改的竞态

需求：站点上还有在用或部署中的设备时，不允许停用这个站点。直觉的写法是：

```txt
1. SELECT COUNT(*) FROM deployments WHERE site_id = ? AND status IN (...)
2. 如果结果是 0：UPDATE sites SET status = 'disabled' WHERE id = ?
```

问题出在第 1 步和第 2 步之间。PostgreSQL 默认的隔离级别是**读已提交**：一个事务只能看到其他事务**已经提交**的数据。考虑下面这个时序：

| 时间 | 事务 A：停用站点 | 事务 B：往该站点发货 |
|---|---|---|
| t1 | | 插入一条部署记录（未提交） |
| t2 | 统计部署数，看不到 B 的未提交数据，结果为 0 | |
| t3 | 停用站点，提交 | |
| t4 | | 提交 |

最终结果是：一个已停用的站点上挂着一台设备，违反了业务规则。

### 方案一：悲观锁

两边都先锁住站点这一行，让它们串行执行：

```sql
-- 事务 A：停用
SELECT * FROM sites WHERE id = ? FOR UPDATE;   -- 排他锁
SELECT COUNT(*) FROM deployments WHERE ...;
UPDATE sites SET status = 'disabled' WHERE id = ?;

-- 事务 B：发货
SELECT status FROM sites WHERE id = ? FOR SHARE;   -- 共享锁
-- 如果 status 已经是 disabled，拒绝发货
INSERT INTO deployments ...;
```

`FOR UPDATE` 和 `FOR SHARE` 互相冲突，所以 A 和 B 只能一个等另一个提交：

- **B 先拿到锁**：A 等 B 提交后再统计，这时能看到 B 刚插入的部署记录，统计结果不为 0，拒绝停用。
- **A 先拿到锁**：B 等 A 提交后才拿到锁，读到的站点状态已经是 `disabled`，拒绝发货。所以 B 加锁之后**必须检查站点状态**，只加锁不检查是不够的。

多个发货事务之间都只加 `FOR SHARE`，彼此不冲突，不会因此互相阻塞。

### 方案二：乐观锁

资产表上有一个 `version` 字段，更新时带上读取时看到的版本号：

```sql
UPDATE assets
SET ..., version = version + 1
WHERE id = ? AND version = ?;
```

如果影响行数是 0，说明这一行在读取之后被别人改过，返回 409，让用户刷新后重试。

### 为什么停用站点不能用乐观锁

乐观锁只能发现**同一行**被别人修改过。停用站点的风险，来自**另一张表**里新插入的部署记录，站点这一行本身并没有被修改，版本号检测不到这种冲突。所以这里只能用悲观锁。

| | 乐观锁 | 悲观锁 |
|---|---|---|
| 做法 | 不加锁，提交时核对版本号 | 先加锁，其他事务等待 |
| 适合 | 冲突少、只涉及同一行的修改 | 先查后改、冲突代价大、涉及多张表 |
| 冲突时 | 返回 409，由用户重试 | 后来的事务排队等待 |

## 小结

| 问题 | 结论 |
|---|---|
| 一对多怎么存 | 外键放在“多”的那一方；被引用的数据只停用、不删除 |
| 跨系统怎么识别同一实体 | 用双方都有的稳定标识（SN），写入前标准化，并加唯一约束 |
| 别人的数据怎么用 | 按对方 id 定时同步到本地，作为只读副本；消失的只停用，空结果不处理 |
| 历史记录怎么保真 | 引用用来读当前值，快照用来记录当时的事实 |
| 列表统计怎么查 | `IN` 加 `GROUP BY` 一次查完，避免 N+1 |
| 要保留没匹配上的行 | 用 `LEFT JOIN`，把不能少的那张表放左边 |
| 会话存哪里 | 多实例共享的 Redis，并设置 TTL |
| 先查后改怎么防竞态 | 同一行的冲突用乐观锁；跨表的规则用悲观锁 |
